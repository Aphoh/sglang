# Decode-to-Decode Migration Roadmap

## Ownership

Dynamo selects workers and decides when to migrate. SGLang owns request-local
parking, the exact KV frontier, NIXL transfer, destination admission, and
cleanup.

Every worker started with `--enable-decode-migration` can send and receive.
`decode/fast`, `decode/slow`, and benchmark-specific roles are Dynamo taints,
not SGLang engine modes.

## Current One-Shot Flow

1. Dynamo selects and reserves a destination before the trigger. It describes
   the source transport and starts the destination generate stream, which
   allocates request-local KV capacity and establishes NIXL connectivity while
   source decode continues normally.
2. Dynamo observes the source token stream and applies its configured migration
   policy. SGLang does not know whether the trigger was a sequence length, token
   ID, model parser event, or an external scheduling decision.
3. Dynamo sends a generic source quiesce command with the number of output tokens
   it has acknowledged. SGLang removes only that request at its next safe decode
   boundary.
4. SGLang exports the acknowledged committed/logical frontier. If overlap
   execution or stream buffering advanced internally beyond it, the unseen suffix
   is excluded and regenerated by the destination.
5. A dedicated source posting lane issues NIXL writes without waiting for prior
   writes to finish. A separate completion lane observes source completion, so
   multiple migrations can be in flight without contending on concurrent calls
   into one NIXL agent.
6. The transferred auxiliary row carries the exact token frontier. On NIXL
   notification, the destination binds that state and enters the normal
   disaggregated-decode admission queue; no late arm or bind RPC is required.
7. Dynamo splices valid destination output into the stream and commits source
   cleanup asynchronously. Source transfer completion never gates destination
   generation.

The source retains the parked request and KV until commit or cancellation, but
there is no resume-after-failed-handoff protocol. Failure aborts the transaction
and performs cleanup.

## Required Invariants

- The engine is never paused globally.
- Overlap scheduling remains enabled.
- Unrelated requests and independent migrations continue running.
- The exported frontier is numeric and exact; stream chunk boundaries do not
  define KV ownership.
- Prepare and quiesce are separate operations. Preparing a source never parks it,
  and quiescing has no trigger-policy fields.
- The destination receives committed KV plus exactly one pending sampled token.
- Tokens already emitted by the source are never replayed.
- Requests that finish before parking are not migrated.
- Cancellation releases request rows, KV pages, metadata buffers, receivers,
  senders, and Dynamo reservation state.
- Source and destination model, page size, dtype, KV layout, PP layout, and
  transfer protocol must be compatible.

## Validation Status

Focused tests cover generic prepare/quiesce separation, acknowledged-frontier
construction, overlap overshoot, destination admission, stream intervals, finish
races, cancellation, rollback, and cleanup. Dynamo separately tests sequence and
token-ID trigger policy.

The generic API was validated locally with Qwen3-0.6B TP1 -> TP1 on two B200s,
NIXL, overlap scheduling, and `--stream-interval 10`. Dynamo supplied a generic
sequence-length policy; SGLang received only prepare, quiesce, and finalize
operations.

A sustained 60 RPS run at concurrency 64 used ISL 1, a truncated-normal OSL
(mean 522, standard deviation 96, bounds 320-704), and a 50/50 source/destination
split. All 256 measured requests plus 60 warmup and 60 cooldown requests
completed. Internal timings over all 376 migrations were:

```text
Dynamo trigger -> source quiesce       p50 18.0 ms, p95 51.6 ms
source quiesce -> first destination    p50  1.6 ms, p95 18.9 ms
Dynamo trigger -> first destination    p50 21.7 ms, p95 58.5 ms
source NIXL issue -> completion         p50  2.8 ms, p95 10.5 ms
```

A synchronized 64-request burst completed 64/64 in 1.28 seconds. Its p50
trigger-to-first-destination time was 101 ms, including 67 ms to deliver and
quiesce the simultaneous controls and 71 ms source transfer service under the
64-transfer wave. This is a contention stress case, not the rate-matched latency.

Deterministic source-only and migrated runs matched all 32 complete token-ID
streams exactly. Live lifecycle checks cover finish-before-trigger,
cancel-after-handoff, and a successful migration immediately after cancellation.

Live validation includes TP1 -> TP1, TP4 -> TP1, MLA transfer, and TP2 -> TP1.
The current static Qwen3-32B confirmation completed 256/256 measured migrations
at an exact 307/308 frontier with overlap enabled.

The confirmed local Pareto point compares pure TP4 with TP2 -> TP1 migration:

```text
Pure TP4:       1.300 req/s/GPU, P95 TTFNT 7.646 s
TP2 -> TP1:     1.692 req/s/GPU, P95 TTFNT 7.424 s
```

See `measurement_plan.md` and `measurement_results_qwen3_32b.md`.

## Next Engineering Steps

### Hard destination leases

Replace advisory reservation state with request-pool and KV-capacity leases.
Leases need capacity, rank, compatibility fingerprint, TTL, and idempotent
reserve/grow/arm/activate/abort transitions.

### Incremental KV synchronization

Reuse the same destination lease, migration ID, bootstrap room, and explicit rank
mapping. While source decode continues, copy monotonically increasing stable KV
ranges. At the trigger, park the request and transfer only the final delta. The
current activation, stream reconciliation, and commit protocol should remain
unchanged.

### Compatibility and DP

Publish cache-layout capabilities and reject incompatible pairs before arming the
source. Add multi-DP tests proving that control RPCs and NIXL handshakes reach the
selected rank.

### Fault injection and observability

Add phase timings, byte/page counts, lease age, and terminal-state metrics. Test
allocation failure, transfer timeout, lost control responses, worker loss,
lease expiry, cancellation at every phase, and rank mismatch.

### Production policy

Use measured reasoning/visible token distributions to choose fast/slow GPU
allocations. Pre-reserve only when predicted boundary timing and KV headroom make
it worthwhile. Incremental transfer is justified only when its TTFNT reduction
exceeds added transfer traffic and reserved-KV cost.
